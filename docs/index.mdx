## Start with a surface

The same `opensre` binary runs everywhere. Pick a surface, install it, and start your first session.

<Tabs>
  <Tab title="Interactive shell">
    Install with one command, sign in, and pick a demo or type a request.

    ```bash
    curl -fsSL https://install.opensre.com | bash -s -- -dc
    opensre
    ```

    Windows uses PowerShell; see [Install](/install). The first prompt offers the CI/CD analysis of a repository on your machine, or skip it with **E**.

    <Frame>
      ![The CI/CD reliability report the first demo produces](/images/onboarding-ci-analysis-report.png)
    </Frame>
  </Tab>
  <Tab title="Headless CLI">
    One agent turn from a script or a CI job, with JSON output and exit codes.

    ```bash
    opensre --json ask "how many PRs currently have failing CI in Tracer-Cloud?"
    ```

    See [Headless CLI](/guides/headless-cli) for `--allowed-tool` and stdin prompts.
  </Tab>
  <Tab title="Slack">
    Mention OpenSRE in a channel or DM it, and hand off DevOps chores to the team's agent.

    Demo option **D** in the shell connects Slack; see [Slack](/integrations/messaging/slack).
  </Tab>
  <Tab title="Managed gateway">
    An organization admin provisions a hosted gateway at app.opensre.com; repairs and scheduled loops run there with the organization's credentials.

    See [Keep CI green with an agent](/cicd/ci-repair-agent#the-managed-service) and [Deployment](/guides/deployment#opensre-cloud-managed-gateway).
  </Tab>
</Tabs>

## How a turn runs

Say an alert fires and you paste it in:

1. OpenSRE reads the alert and decides what kind of problem it is looking at.
2. It gathers context: who owns the service, what changed recently, what is normal.
3. It checks the tools you connected for logs, metrics and traces.
4. It keeps digging and testing ideas until it can answer.
5. It answers in the shell and sends the result where you asked: Slack, Telegram, a file.
